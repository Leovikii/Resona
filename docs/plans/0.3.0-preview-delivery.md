## 推荐方案

Windows 沿用 NSIS 安装和 Tauri 签名更新。Linux 只交付 Arch 原生安装包与 AUR `-bin` 配方，依赖使用 Arch 系统库，软件内提供包管理器更新引导。Linux 不构建 AppImage，也不实现应用内下载、替换或提权安装的自更新链路。

| 安装方式 | 交付物 | 更新方式 |
| --- | --- | --- |
| Windows | NSIS `currentUser` 安装包 `.exe` | Tauri 下载、验签、覆盖安装 |
| Arch / AUR，主要入口 | 暂定 `resona-preview-bin` 的 `PKGBUILD`、`.SRCINFO` | yay/paru 获取新构建，再由 makepkg/pacman 安装 |
| Arch 直接安装 | 与 AUR 配方相同的 `.pkg.tar.zst` | 手动 `pacman -U`；安装本地包不会自动获得更新仓库 |

AUR 存放构建配方，不托管应用二进制；`-bin` 配方从固定 GitHub Release 下载已编译载荷，再由 makepkg/pacman 安装。CI 用同一配方生成 `.pkg.tar.zst`，方便直接下载安装。支持范围保持 Arch x86_64 / Wayland。

## 版本不变，构建可识别

应用版本与发行构建身份分开：

| 字段 | 示例与规则 |
| --- | --- |
| 应用版本 | `0.3.0-alpha.1`，源码、程序关于页和安装器保持一致 |
| 构建序号 | 同一个交付工作流的 `github.run_number`，例如 `42` |
| 重试序号 | `github.run_attempt`，例如 `1` |
| 构建身份 | `b42.1-g00e1be2`；完整 commit SHA 写入元数据 |
| Release tag | `preview-v0.3.0-alpha.1-b42.1-g00e1be2` |
| Release 标题 | `Resona 0.3.0-alpha.1 · Preview build 42.1` |
| Arch 包元数据 | `pkgver=0.3.0alpha1`，`pkgrel=42.1` |

例子中的编号仅说明格式，不表示已存在的 GitHub 构建。Arch 的包修订号会增加，以便包管理器识别更新；这不修改应用版本，也不把 `alpha.1` 改为 `alpha.2`。

- CI 一次生成构建元数据，供两平台、安装包、Windows 签名更新清单和 AUR 配方共同使用；程序编译时嵌入版本、构建序号、重试序号、完整 SHA 和通道。关于页另显示构建身份，反馈问题时能确定实际运行包。
- 构建序号按数字二元组 `(run_number, run_attempt)` 比较；时间只用于显示，SHA 只用于确认身份，不能按字符串或时间判断新旧。
- 发布后的 tag、构建身份和资产保持不变。重试已公开的构建必须使用新身份，不能覆盖旧二进制或移动旧 tag；已公开资产的修复也不能复用原身份。
- `+build` 不参与 SemVer 优先级，单纯添加它不能解决本需求。预览 tag 由专门解析器识别，不能继续把所有 tag 去掉 `v` 后当作应用版本。
- 保留当前交付工作流文件作为编号来源；未来迁移工作流时先建立连续编号策略，不能让新工作流从小编号重新发布。

本机 `vercmp` 已验证以下顺序，实施时加入脚本回归：

```text
0.3.0alpha1-42.1 < 0.3.0alpha1-42.2 < 0.3.0alpha1-43.1
0.3.0alpha1-43.1 < 0.3.0alpha2-1 < 0.3.0-1
```

## CI/CD 流程

继续使用现有单一 `main-merge-delivery.yml` 和受保护的 main；本方案不增加手工 tag、手工发布工作流或开发分支读取发布密钥的入口。

| 触发 | 计划行为 |
| --- | --- |
| 目标为 main 的 PR | Windows、Arch 验证，汇总为既有 required check `PR validation`；无发布秘密或外部写入 |
| main push，应用版本为预发行 | 对需要交付的提交生成新构建身份，验证、构建并发布 GitHub prerelease；同一应用版本允许多次预览构建 |
| main push，应用版本为稳定版 | 保留既有版本递增与唯一 `v<version>` tag 规则 |
| 纯文档、图片说明等不影响交付的 main 提交 | 检查通过后跳过发包；路径分类必须显式覆盖运行资源、构建脚本、安装配方和锁文件 |

预览 Release 一律 `prerelease=true`、`make_latest=false`。稳定用户默认不接收预览；现有稳定版下载入口和稳定更新发现不能被预览构建接管。dev 继续用于开发，本轮不会因设计文档落盘而触发发布。

main 交付分为以下 job，均检出同一个已解析的完整 SHA：

1. **交付判定与验证**：检查版本文件一致、变更范围、构建身份、tag 冲突；复用 Windows/Arch 自动检查。main 交付也需验证，不能只依赖曾经运行过的 PR 检查。
2. **两平台构建**：验证完成后分别生成 Windows NSIS 和 Linux 载荷、Arch 包。Windows 构建只在受 main 约束的 `release` Environment 注入 Tauri 签名秘密；Linux 构建不需要 Tauri 签名私钥，构建任务没有 Release 写权限。
3. **统一发布**：一个 job 汇总两平台资产，生成 SHA-256 与更新清单，验签并检查平台资产齐全；先上传 draft，全部成功后再公开。不要让两个平台分别覆盖同一个 `latest.json`。
4. **AUR 同步**：GitHub Release 公开且固定下载地址可取后，推送该构建的 `PKGBUILD` 和 `.SRCINFO`。只传递已验证的 tag、SHA 和校验值；AUR SSH 密钥与 GitHub 发布凭据分开。

某个平台失败时不公开这一轮 Release。公开前失败保留 draft 供诊断；公开后禁止补写不同内容到既有资产。旧运行的重试不得把较新构建的 AUR 配方降回旧编号；并发串行化仍要保留。

AUR 同步是独立外部提交，无法与 GitHub Release 原子完成：失败时 GitHub 下载仍可用，任务明确失败并可重试同一组配方；不能因此覆盖或删除已公开资产，也不能把发布状态写成“AUR 已上线”。

首个 AUR 包仍需所有者确认包名可用、维护者账号与 SSH 权限。工作流默认不推送 AUR；配置方式见下方实施记录。本次不注册包或修改远端 Environment。

## 安装包与目录

每个预览 Release 交付：

| 资产 | 用途 |
| --- | --- |
| `Resona_<version>_<build>_windows_x86_64-setup.exe` 与 `.sig` | Windows 首次安装和 Tauri 更新 |
| `Resona_<version>_<build>_arch_x86_64.tar.gz` | AUR 预编译载荷，含运行资源、桌面入口、图标和许可证 |
| `resona-preview-bin-<pkgver>-<pkgrel>-x86_64.pkg.tar.zst` | 由同一配方生成，可直接用 pacman 安装 |
| `PKGBUILD` 与 `SRCINFO` | 公开配方副本；`SRCINFO` 内容与 AUR 的 `.SRCINFO` 相同，下载后用于 AUR 时恢复点前缀 |
| `latest.json` 与 `latest.json.sig` | 同一构建的 Windows 更新清单及完整清单签名 |
| `SHA256SUMS`、对应源码归档及第三方声明 | 手动校验与许可证交付 |

`latest.json.platforms` 只放 Windows NSIS，不添加 Linux 条目。Arch 原生包只进入 Release 资产清单与 SHA-256 清单，不接入 Tauri updater。

GitHub 会重命名点开头的 Release 资产（实际将 `.SRCINFO` 改为 `default.SRCINFO`）；因此公开资产及 `SHA256SUMS` 使用 `SRCINFO`，Actions 内部 artifact 和 AUR 仓库继续使用 `.SRCINFO`。公开前严格核对草稿资产名称，失败时打印期望/实际列表并保留草稿；修复合并到 main 后使用新构建身份交付，不覆盖旧草稿或已公开资产。

Arch 原生包安装到 `/usr/bin/resona`、`/usr/lib/Resona/`、标准 applications/icons/licenses 目录，按 Tauri 实际资源解析路径验证；不携带本机测试包的 `test-profile/` 或用户字体链接。普通用户运行，用户数据仍遵循系统 XDG 目录。

原生包通过依赖声明使用系统 GTK、WebKitGTK 4.1、gtk-layer-shell、ALSA 与 Tauri 托盘依赖；准确列表以二进制链接检查和干净 Arch 环境验证为准，不直接抄构建依赖。FFmpeg 为压缩功能的可选依赖，PipeWire 桌面建议 pipewire-alsa，KDE 文件选择建议对应 portal；程序不运行 pacman、不提升权限。

Arch 滚动更新引起库 ABI 变化时，可在同一应用版本下重建并增加包修订号；构建记录应保留实际使用的系统包版本，方便定位二进制兼容问题。

入口固定 Wayland，保留启动参数转发。`.desktop`、图标与 MIME 声明由包安装，但不抢用户默认播放器；卸载不删除用户列表、偏好或音频。

## AUR 配方

- 预览阶段建议使用 `resona-preview-bin`；未来正式 Linux 版本使用 `resona-bin`，包名仍待可用性确认。两者提供同一个应用并互相 conflicts，不在同一数据标识下并行安装两份。
- `pkgver` 将 `0.3.0-alpha.1` 映射为 `0.3.0alpha1`；`pkgrel` 使用构建二元组。未来更高应用版本重置包修订；不要为这轮预览引入 `epoch`。
- `source_x86_64` 指向唯一 tag 下的唯一载荷 URL，写入真实 `sha256sums_x86_64`；禁止 `latest`、浮动分支或 `SKIP`。
- `package()` 只把已验证二进制和资源安装到 `$pkgdir`，不在用户机器编译 Rust、不联网更新配方、不运行程序、不启动服务。
- CI 使用普通构建用户执行 makepkg，不能在 Arch 容器的 root 用户下直接运行；用干净构建环境和 namcap 检查依赖、目录、权限与 `.SRCINFO` 一致性。
- 先在 GitHub 仓库内维护配方模板/生成输入，发布后同步到 AUR 专属 Git 仓库；AUR 内不提交二进制、测试数据或签名私钥。
- SHA-256 是内容校验，不能当作发布者签名。Tauri updater 签名不等于 pacman 包签名；第一轮不自建 Arch 二进制仓库，不能暗示 pacman 会自动信任从 GitHub 下载的包或自动订阅更新。

## 应用内更新

### Windows 与 Linux 分别处理

沿用现有 Rust distribution adapter 的 Windows updater 能力边界，不为 Linux 新增安装来源探测或自更新状态机。

- **Windows NSIS**：复用当前启动后单飞检查、关于页主动检查、Release 说明、用户确认下载、进度、取消与 Tauri 验签；不后台静默下载或安装。
- **Linux**：关于页显示“由包管理器更新”，将“检查更新 / 下载并安装”替换为“更新说明”。不启动后台版本轮询，不为更新请求 GitHub/AUR，不显示 Tauri 的下载进度或“接收预览版”开关；预览/稳定由安装的 AUR 包决定。
- **引导内容**：AUR 用户可复制 `yay -Syu` 或 `paru -Syu`，并打开实际发布的 AUR 包页面。用户自行在终端运行，应用不自动执行命令、不安装 AUR helper，也不运行 sudo/pacman。说明使用完整更新，避免引导 `-Sy` 后的部分升级。
- **直接安装 `.pkg.tar.zst`**：说明该方式不会订阅更新仓库，提供 GitHub Release 下载入口和手动 `pacman -U` 安装说明；如果希望持续更新，可改用 AUR 配方。包内测试数据迁移仍需单独说明。
- **本机测试包**：引导安装新的 Arch 包，保留原隔离数据；不能宣称已纳入包管理器。页面同时说明 AUR 和手动安装两种路径即可，不探测 yay/paru 或读取 pacman 数据库。
- **后端约束**：Linux 安装更新 command 始终拒绝，不能只依靠隐藏前端按钮阻止安装；Linux updater 的 `supported=false` 保持有效。

### Windows 同版本预览更新

`latest.json.version` 仍为 `0.3.0-alpha.1`。清单增加 Resona 专用的 schema、通道、构建二元组和完整 SHA；每个平台条目保持 Tauri 所需的 URL 与安装包签名。CI 对完整 `latest.json` 另外签名，用相同发布公钥和成熟的 Minisign 验证实现校验构建身份；Tauri 继续验证安装包自己的签名，两层不能互相替代。

Windows 更新服务先读取并验证清单签名，再检查预览 opt-in、应用版本、安装格式、架构和构建身份。比较规则：

1. 更高应用版本按 SemVer 优先级选择，稳定用户排除预览；低版本不能因构建编号大而变成更新。
2. 应用版本完全相同，且两者属于该预览通道时，只接受构建二元组更大的构建。
3. 身份相同不重复提示；较旧构建不自动回退；身份相同但 SHA/资产映射不同视为发布错误。
4. 安装前固定具体 tag、构建身份、平台、URL 与签名，不能只传 `expected_version` 然后重新选择“最新”包。
5. 使用现有 Tauri Rust `UpdaterBuilder::version_comparator` 为这个已选定、已验证的同版本构建放行，并核对 Tauri 返回的版本、目标 URL 与签名。不能使用无条件返回 true 的比较器。

当前 updater 的 `RemoteRelease` 不直接暴露这些 Resona 扩展字段，因此由业务服务先解析；比较器使用已验证的选择结果，不假设插件会自动理解构建编号。若需要显式依赖现有签名验证 crate，应锁定兼容版本并补依赖/许可证审查，不实现自有密码算法。

发布后的完整清单保持不变，清单签名最后生成。预览和稳定各自从 GitHub Release 选择固定清单，不需要自建更新服务器或维护会被并发覆盖的全局“最新预览”资产。

首个具备构建识别能力的 Windows 预览包建议手动安装：当前旧客户端不能解析新预览 tag，也不认识构建编号；不能承诺它们会自动发现这一轮同版本更新。Linux 的同版本构建更新完全由递增的 Arch `pkgrel` 识别，无需接入上述清单比较器。本机 Linux 测试包到原生安装包的首次安装需迁移指引：测试数据在包内，安装版使用正常 XDG 数据，禁止自动删除或覆盖原测试数据。

预览与稳定继续共用现有应用标识，不新增并行安装的第二套数据库。Windows 安装预览会替换现有安装；说明中明确这一点。未来稳定版本提高 SemVer 后自然高于当前 alpha 构建；构建序号不得阻挡这条升级路径。

## 验证与实施顺序

| 阶段 | 实施内容 | 放行条件 |
| --- | --- | --- |
| 1：构建身份与发布规则 | 元数据生成、tag 解析、Windows 版本/构建比较、DTO、Arch 包修订 | 同版本更新、稳定隔离、重复运行、旧运行重试、降级拒绝的回归通过 |
| 2：可安装资产 | Windows NSIS、Arch 载荷与包、配方校验 | 干净环境可安装/启动/卸载，资源完整，用户数据保留；两个 Arch 包修订之间可升级 |
| 3：平台更新体验 | Windows 清单/安装包签名与 Tauri 衔接，Linux 包管理器引导 | 两个同版本不同构建之间的 Windows 真更新成功，签名错误/取消不覆盖原安装；Linux 命令复制和外链正确，无更新网络请求或进程启动，后端拒绝自更新 |
| 4：CI/CD 联调 | 两平台同一 SHA 构建、单 job 发布、AUR 后置同步 | draft 不提前公开，失败不发布半套包，AUR 重试不降级，稳定入口不变 |

原生验收继续覆盖 KDE 的桌面歌词 overlay/穿透/解锁、MPRIS、托盘、系统字体和窗口尺寸，不能以容器构建通过替代这些项目。Windows 需实测同版本 NSIS 覆盖安装与卸载；源码中的同版本安装分支只证明存在该路径。

建议新增自动检查覆盖：版本文件始终不变、Arch 包版本顺序、Windows 主版本优先于构建编号、错误/缺失清单签名、清单与资产不匹配、Windows 同版本不同构建的安装请求绑定、Linux 禁止自更新及无后台更新网络请求、两平台齐全才公开，以及 AUR `.SRCINFO`/摘要与 Release 载荷一致。

首个公开预览前还需准备 Windows 更新发布公钥/私钥、AUR 账号与包名、AUR 专用 SSH 凭据，确认 GitHub `release` Environment 的 main 限制和所需写权限。沿用当前 Windows Authenticode 非门禁策略；Windows 提供 Tauri 签名，两平台提供 SHA-256，并披露 SmartScreen 的现有限制。

## 实现与运行配置（2026-10-27）

- `.github/workflows/main-merge-delivery.yml` 在 PR 与 main 都运行两平台验证；PR 保持 `PR validation`。只有 main push 且交付路径发生变化才进入构建发布；推送 dev 不发布，本机不运行发布脚本。
- Windows 通过官方 Tauri CLI 构建并签名 NSIS，仅上传 Actions 中间产物；Arch 通过 `package-arch.mjs` 生成载荷，由普通用户运行同一 PKGBUILD。发布 job 汇总、验签、生成源码与 SHA256SUMS，确认 draft 资产完整后公开。
- `minisign-verify = 0.2.5` 已由锁定 Tauri updater 使用，本次仅声明直接依赖，不增加新版本/下载/遥测；MIT 许可证兼容项目。清单验证使用相同的 Tauri base64 Minisign 格式，测试仅保留一次性测试公钥和签名，无测试私钥。
- 安装包的 ELF 位于 `/usr/bin/resona`，Tauri 资源位于 `/usr/lib/Resona`。进程在初始化 GTK/工作线程前选择原生 Wayland。标准 `.desktop` 通过 `%F` 转交文件，注册 MP3、WAV（含 `audio/vnd.wave` 与旧别名）、FLAC 和应用图标；依赖 desktop-file-utils/hicolor-icon-theme，使用 pacman 标准钩子维护缓存，不覆盖用户默认播放器配置或删除用户数据。
- Linux 关于页提供更新说明、命令复制和 AUR/Release 链接，显示构建身份。启动不会调用更新检查；后端 capability 继续拒绝 Linux 自更新。Windows 安装请求使用检查时缓存的固定 tag/清单身份/安装器 URL/签名，不重新选择最新构建。
- 两个平台都通过显式的 `RESONA_BUILD_NUMBER`、`RESONA_BUILD_ATTEMPT`、`RESONA_BUILD_SHA` 嵌入身份。本机构建默认无发布身份；本机测试注入的编号不能用于上传。只重跑失败的构建 job 会造成构建身份不一致并拒绝发布，此时应重跑全部构建。仅 AUR job 失败可以单独重跑，不重发 Release。

### GitHub 配置

| 位置 | 配置 | 用途 |
| --- | --- | --- |
| `release` Environment，限制 main | variable `RESONA_UPDATER_PUBLIC_KEY`；secrets `TAURI_SIGNING_PRIVATE_KEY`、`TAURI_SIGNING_PRIVATE_KEY_PASSWORD` | 沿用既有 Windows 安装器签名，发布 job 同时签名/验证完整清单 |
| repository variable | `RESONA_AUR_ENABLED=true` | 所有者准备好账号与包名后开启 AUR 同步；未开启仍正常发布 GitHub 双平台安装包与配方 |
| `aur` Environment，限制 main | secret `RESONA_AUR_SSH_KEY`；variable `RESONA_AUR_KNOWN_HOSTS` | 独立 AUR 部署密钥与经官方渠道核对的 SSH 主机公钥；严格校验主机，不临时信任 ssh-keyscan 的结果 |

`scripts/sync-aur.sh` 先下载公开固定 URL 并验 SHA-256，再与远端 `.SRCINFO` 使用 `vercmp` 比较。相同版本配方必须逐字相同；旧版本拒绝推送；推送不是 force。首次启用前，所有者需确认 `resona-preview-bin` / `resona-bin` 包名和维护权限。应用的 AUR 页面在包首次同步前可能尚不存在。

### 本轮验证边界

本机测试与安装包只留在忽略的 `src-tauri/target`，不提交或上传。自动检查覆盖构建/版本顺序、配方解析与校验、两平台身份/资产缺失拒绝、清单有效签名与篡改拒绝、实际音频 MIME 匹配。测试结果与原生回归结论见 [STATUS](../STATUS.md)。

GitHub main 首轮双平台构建、签名与 Arch 安装/卸载已通过；公开发布因 `.SRCINFO` 重命名停在草稿，修复后的发布与 AUR 同步仍需合并后的 Actions 实际执行。Windows 同版本 NSIS 覆盖、安装/卸载和原生回归仍需 Windows 环境，不把本机 Linux 测试视作已验收这些项目。
