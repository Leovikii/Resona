# 0.2.0 本地专辑播放增强

- 状态：Completed
- 开始日期：2026-07-28
- 完成日期：2026-07-28

## 目标

- 同名 CUE 由 Rust 在导入阶段解析为有明确起止时间和元信息的逻辑音轨；播放列表、队列、定位、切歌和持久化均使用同一媒体源模型。
- 当前曲目封面按“内嵌封面、同目录 `cover` 图片、目录唯一图片、多图中的小尺寸方图”回退；目录扫描、源文件和解码尺寸保持有界，归一化结果继续共享给 React、SMTC 与任务栏。
- 桌面歌词极长单行只从头到尾线性滚动一次，进度与该行实际展示区间及播放位置同步；暂停、定位和减少动态效果均保持稳定。
- 播放列表曲目右侧显示时长，目录段和整表显示合计；CUE 展示逻辑分轨时长，摘要读取保持分批、有界且不解析封面。

## 实施与门禁

- CUE 支持 UTF-8、UTF-16 与 GBK 文本，解析失败不阻止原音频作为普通文件导入；同一物理文件的多个逻辑音轨不得被路径去重合并。
- SQLite 迁移必须保留 0.1.0 播放列表；普通文件的现有行为和旧播放会话格式保持兼容。
- 封面只扫描音频直属目录中的 JPEG/PNG，候选数量、文件字节、像素和缓存条目均有上限，候选排序必须确定。
- 自动验证覆盖 CUE 解析与区间、播放列表迁移、封面优先级/边界和歌词动画计算；通过前端测试与构建、Rust format/test/clippy、许可证和工作流检查。
- Windows 实机验收已覆盖 CUE 连续切轨/定位、SMTC 与任务栏封面回退、桌面歌词暂停/定位、长句滚动和置顶恢复，未发现阻断发行的新问题。

## 已实施：Windows 桌面歌词置顶稳定性

### 诊断

- 当前窗口创建时同时声明 Tauri `always_on_top` 和 Win32 `WS_EX_TOPMOST`，显示、锁定、解锁、字号适配、歌词窗口失焦、DPI 变化及应用 `Resumed` 时再调用无激活的 `SetWindowPos(HWND_TOPMOST)`。重建窗口能恢复，说明窗口句柄、透明 WebView 和基本置顶调用本身可用。
- Windows topmost 是共享的 Z-order 分组，不是不可被其他窗口超过的绝对层。其他程序在之后激活或重新声明 topmost、虚拟桌面切换、显示器/睡眠恢复都可能重排该分组；独占全屏、安全桌面及部分系统表面本来就不受普通应用保证。
- 现有触发覆盖不足是最高概率原因。歌词窗口失焦只会发生在它曾经获得焦点之后；锁定窗口会穿透且原生 helper 使用 `WS_EX_NOACTIVATE`，外部窗口继续切换时通常不会产生新的歌词 `Focused(false)`。`RunEvent::Resumed` 也不是每次 Windows Z-order 重排的完整信号。
- 单看 `WS_EX_TOPMOST` 是否仍存在不足以诊断：窗口可以仍属于 topmost 分组，却排在后来置顶的窗口之后。没有稳定复现前，不把问题归因于 WebView2、透明窗口或锁定状态中的任何一个单点。

### 实际实现

1. 在 Windows desktop-lyrics adapter 内增加与窗口资源同生命周期的 `SetWinEventHook` 观察器，监听 `EVENT_SYSTEM_FOREGROUND`、`EVENT_SYSTEM_DESKTOPSWITCH` 和 `EVENT_SYSTEM_MINIMIZEEND`。使用 `WINEVENT_OUTOFCONTEXT | WINEVENT_SKIPOWNPROCESS`；隐藏/销毁歌词资源时必须 `UnhookWinEvent`。
2. WinEvent 回调只向 Tauri 主线程投递“校正置顶”意图，并用单个 pending 标志合并突发事件；Win32 回调内不获取服务锁、不调用 Tauri/WebView 窗口 API，也不等待主线程。
3. 合并后的任务在 Tauri 主线程读取仍有效的窗口资源，再沿用一次 `SetWindowPos(HWND_TOPMOST, SWP_NOACTIVATE | SWP_NOMOVE | SWP_NOSIZE)`；歌词窗口先校正，锁定 helper 后校正，从而保持 helper 位于歌词之上且全程不抢焦点。
4. 第一版不执行 `HWND_NOTOPMOST → HWND_TOPMOST` 双切换。直接校正已能同时恢复丢失的 topmost 标志和 topmost 分组顺序，双切换会增加闪烁及短暂落入普通窗口层的风险；只有实机证据表明单次校正成功返回但层级仍错误时，才增加经过验证的有限回退。
5. 不使用定时轮询、前端播放快照顺带保活、`SetForegroundWindow`、`BringWindowToTop`、低级全局 hook 或 `RegisterShellHookWindow`，也不新增第三方窗口依赖。现有 `windows` crate 只补充官方 `Win32_UI_Accessibility` feature。

实际实现还为每次歌词窗口资源分配独立代次；隐藏或快速重建后，旧观察器已经排队的主线程任务不会作用于新窗口。三个不连续事件分别安装 hook，避免为覆盖区间而订阅无关系统事件。

### 诊断与验收

- 自动测试覆盖精确事件集合、突发事件合并和资源代次判断；Rust 编译与 Clippy 校验 Win32 hook 的安装/释放路径。失败日志保留事件类型和 Win32 错误，不为每次前台切换写日志。
- Windows Release 已完成锁定与解锁状态下的实机交互验收，暂未发现新问题；普通窗口连续切换、Win+D、虚拟桌面及系统恢复场景继续作为后续回归清单保留。
- 预期是普通窗口及后来进入 topmost 分组的普通应用窗口切换后，歌词在一次事件校正内恢复且不获取焦点。独占全屏、安全桌面、UAC 安全提示不纳入可覆盖承诺；若两个应用都持续争夺 topmost，遵循 Windows 最近一次有效 Z-order，不建立对抗式循环。
- 完成门禁：前端 42 项测试、Rust 111 项通过（9 项设备/固定工具测试按设计忽略），生产构建、Rust format、Clippy、许可证、工作流与差异检查通过；Windows Release 实机交互验收由项目所有者完成。
