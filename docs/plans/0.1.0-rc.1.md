# 0.1.0-rc.1 Windows 发布候选收尾

- 状态：Implemented；等待项目所有者原生发行验收
- 日期：2026-07-23
- 前置条件：0.0.19 已完成并通过项目所有者 Windows 安装版验收

## 目标

在功能界面和 Windows 集成冻结的基础上，完成首个公开候选版所需的更新、签名、诊断、性能和发布链路；集中修复发行阻塞缺陷，不新增播放器能力。

原计划中的 0.0.20“更新器与发行加固”完整归并到本阶段，版本序列调整为 `0.0.19 -> 0.1.0-rc.1 -> 0.1.0`。

## 范围

### 更新与发布链

- 开始实现时把 npm、Cargo 和 Tauri 配置中的版本统一切换为 `0.1.0-rc.1`；RC 安装包、更新清单、运行时“关于”和发行说明必须读取同一版本事实。
- 按 [ADR 0024](../decisions/0024-windows-tray-distribution-and-update.md) 使用 Tauri 官方 updater 实现设置“关于”中的主动检查更新、版本/说明/大小展示、下载进度、用户取消和安装前确认。
- “关于”新增“接收预览版更新”开关。稳定构建首次默认关闭；SemVer 含 prerelease 段的构建首次默认开启；偏好在 Rust 更新服务中类型化持久化，用户后续可显式切换。
- 稳定和预览检查统一使用 GitHub 原生 Releases REST API。稳定设置排除所有 prerelease；预览设置接受 prerelease 与稳定版，并按完整 SemVer 选择最高版本。每个不可变版本 Release 自带该版本的签名安装包与 `latest.json`，不维护 `update-preview` 或其他可变通道指针。任何通道都不允许自动降级，无网络、清单损坏、签名错误或下载失败不得影响本地播放。
- GitHub Release 通道完全由版本号决定：`-alpha`、`-beta`、`-rc` 和其他合法 SemVer prerelease 自动标记为 GitHub prerelease；无 prerelease 段的版本进入稳定发布。比较必须满足 `alpha < beta < rc < 正式版`，不能只识别 rc。
- 单一 GitHub Actions workflow 使用两段式边界：目标为 `main` 的 PR 在创建、更新、重新打开和转为 ready 时通过 `pull_request` 运行只读 `PR validation`，该检查作为 ruleset required status check；受 ruleset 保护的 `main` 收到合并 push 后进入轻量 `Prepare delivery`，符合版本发布条件时自动交付。发布事件的 Environment ref 天然为 `main`，不使用 `pull_request_target`，也不放宽到 `refs/pull/*/merge`。流程不配置 tag push 或手工发布旁路，仓库规则禁止直接推送 `main`。
- `PR validation` 验证 GitHub 生成的 PR merge commit，覆盖前端测试/构建、许可证一致性、Rust format/test/Clippy 和 SemVer 发布规则；它不读取 `release` Environment、不构建签名安装包、不创建 tag 或 Release。ruleset 要求分支与最新 `main` 同步后才能合并。
- 合并后的 `Prepare delivery` 检出 `main` push 的精确 `github.sha`，以 `github.event.before` 为比较基线，只执行版本一致性、目标 tag 与 prerelease 判定，不重复运行已经通过的前端测试/build/licenses 和 Rust format/test/Clippy。已有 tag 的同版本合并在判定后自动结束；当前版本尚无 tag 时允许首个合并自动建立初始 Release，之后只有版本变化且新 tag 不存在时才自动进入 CD。CD 的签名 NSIS 构建继续执行分发审计和原生窗口门禁。
- CD 只生成一个 Windows x64 NSIS 安装包及其 updater 签名、更新清单、版本说明和 SHA-256，不维护单独替换程序或第二个安装渠道。`main` delivery 链串行执行并保留等待任务，PR 验证按 PR 取消过时运行且不阻塞 delivery；只有发布 job 授予 `contents: write`，其余 job 保持只读。
- 第三方 Action 固定完整 commit SHA；updater 私钥和未来 Authenticode 凭据只由受保护的 GitHub Environment/Secrets 注入。版本不一致、重复 tag、签名缺失或任一审计失败时不得发布部分产物。
- `release` Environment 只允许 `main`，Required reviewers 与 Wait timer 保持关闭；符合版本条件后自动发布，不要求项目所有者手工批准或启动。
- updater 签名私钥不得进入仓库、安装包或日志；公钥进入应用配置。Windows Authenticode 与 Tauri updater 使用独立信任边界。
- 从已安装的 0.0.19 验证覆盖升级，确认数据库、播放列表、窗口状态、歌词偏好、退出偏好和按需 FFmpeg 状态保持。

### 前端渲染与资源审计

- 先记录基线再改代码：生产 bundle/chunk 大小、冷/暖启动 10 次的中位数和高分位、60 秒空闲/播放 CPU 与内存、React commit 次数、长列表滚动和切歌期间主内容/底栏提交范围。
- 用 React Profiler 和浏览器 Performance 检查当前约 74 KB 的 `App.tsx`、preferences context、播放 `750ms` 轮询、压缩 `250–300ms` 轮询、桌面歌词轮询及隐藏到托盘后的不可见 WebView 工作。
- 只有 Profiler 证明跨区域提交或 bundle/解析成本时才拆分组件、context 或 lazy chunk；不为“看起来模块化”增加无行为包装层。播放与转换领域状态继续由 Rust 权威服务提供。
- 优先减少不必要轮询、重复 `invoke`、全局 context 更新和隐藏窗口工作；可用 Tauri event 替代时仍保留有界失败与恢复策略，不能把权威状态复制到前端。
- 长播放列表只有在真实滚动/提交基线证明需要时才引入虚拟化；引入后必须保持 Ctrl/Shift 多选、双击、右键菜单、Pointer Events 排序和外部文件插入语义。
- 形成 `docs/performance/0.1.0-rc.1.md`，记录机器、Windows/WebView2 版本、数据集、测量方法、前后结果和未采用优化。任何优化不得让关键指标相对基线恶化超过测量噪声或产生新的布局重绘。

### 后端性能与音质审计

- 审查 Rodio actor `150ms` tick、设备轮询、原生播放投影 `500ms` 刷新、锁持有范围、快照克隆、SQLite 查询、元数据/歌词文件 I/O 以及压缩扫描线程；禁止在锁内执行文件、数据库、网络或原生窗口阻塞调用。
- 测量冷/暖启动、60 秒空闲、播放、隐藏到托盘、桌面歌词和音频压缩扫描/转换时的 CPU、内存、线程、文件/数据库访问和 WebView2 子进程状态，只优化有证据的热点。
- 音质检查覆盖 MP3、PCM WAV、FLAC 和 44.1/48/96/192 kHz、16/24/32-bit fixture：核对解码参数、Rodio 输入、CPAL 实际输出流、声道、采样率、定位与设备切换，不把 WASAPI Shared 的系统转换误写成源文件属性。
- 音量路径保持 `0.0..=1.0`，不增加软件增益、响度标准化、EQ、DSP 或未经测量的重采样；验证无意削波、声道错误、静音填充、切歌爆音和恢复后位置错误。
- 在连续专辑、混合采样率、长时播放、暂停/定位、默认/指定设备和蓝牙断开恢复下记录可复现结果。0.1.0 仍不承诺 WASAPI Exclusive、ASIO、bit-perfect 或新增第二播放引擎。
- 不为性能或“音质”自动升级 Rodio/CPAL/Symphonia；依赖变化必须单独审查许可证、API、输出行为和完整 fixture 回归。

### 仓库与公开说明收束

## 自动验收

- 更新器覆盖稳定默认、prerelease 默认、用户切换、有更新、已是最新、稳定通道排除预览版、预览转正式、无网络、无效清单、签名错误、下载失败、取消和安装确认。
- 完整 CI 在目标为 `main` 的 PR 上运行并阻止失败提交合并；ruleset 禁止直接 push，tag push 和手工工作流均不得创建 Release。`main` 的合并 push 后只做轻量版本判定，尚无 tag 的当前版本在首个合并后自动建立一次初始 Release；已有 tag 的同版本合并不得重复发布。SemVer prerelease 自动生成预发行 Release，稳定版本自动生成普通 Release。
- TypeScript/Vite build、许可证生成、Rust format/test、Clippy `-D warnings`、Windows 分发审计、NSIS Release 和原生主窗口可见性门禁通过。
- CI 在干净检出中可重复生成与本地发布结构一致的产物，且不泄露私钥或把 FFmpeg/ffprobe 打入安装包。
- 日志轮转、路径隐私、退出清理、升级保留数据和失败降级有与风险相称的自动测试。
- 前后端性能报告包含可复现实验与基线对照；音频 fixture、实际输出配置和长时播放回归没有音质或稳定性退化。
- 中英文 README 链接、品牌资源、下载入口和能力描述一致；仓库删除项无残余引用，干净检出可以完成完整测试与 Release。

## 项目所有者验收

- 从 0.0.19 安装版执行一次真实更新，确认下载、确认安装、重启和状态保留。
- 在稳定构建开启预览开关收到 RC，在 RC/预览通道收到后续 RC 或正式版；关闭开关后不再收到新的 prerelease。
- 完成仍开放的多显示器、DPI、原生拖入和桌面歌词发行矩阵；记录 Windows 版本、缩放、显示器布局与结果。
- 在干净 Windows 用户下抽查安装、开始菜单启动、文件关联、SMTC、任务栏、托盘、退出和卸载。
- 确认候选版界面无新增功能、明显重绘、不可达操作或发布阻塞视觉问题。
- 审阅英文/中文 README，确认首页简洁、重点准确、下载入口清晰且没有面向 Agent 的内部台账。

## 预计需要项目所有者介入

- 首次生成并离线备份 Tauri updater 私钥，将发布所需私钥配置为 GitHub Actions secret；仓库只保存公钥。
- 决定公开 RC 是否使用 Authenticode 证书或可信云签名，并提供相应发布凭据。未完成前只能生成明确标记的未签名候选测试包。
- 在 GitHub 仓库启用 `main` 分支保护、禁止直接 push，并配置最小 Actions/Environment 权限。
- 安装并验收一次由 GitHub Release 托管的真实更新；在此之前本地模拟更新不能替代端到端结论。

## 完成定义

- `0.1.0-rc.1` 安装包、更新产物、更新清单、版本说明、许可证通知和 SHA-256 相互一致且可重复生成。
- 稳定/预览通道、PR-merge-only CI/CD、版本自动分流、README 双语入口和仓库清理均通过干净仓库验证。
- 前后端审计有量化证据；已实施优化能够解释收益，未实施项记录原因，播放格式矩阵与实际输出没有音质回归。
- 没有未关闭的 P0/P1 发行缺陷；所有暂缓问题均有明确影响、复现条件和公开说明。
- updater 私钥不在仓库、日志或发布包中，断网时播放器核心完整可用。
- 项目所有者完成候选版验收后，进入 0.1.0 正式发布门禁，不再增加产品功能。
