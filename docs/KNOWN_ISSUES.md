# 已知问题

最后更新：2026-07-23

## 外部文件拖入用户播放列表待实机回归

- 状态：0.0.18 纠正性实现已完成，仍阻塞 0.1.0，等待 Windows 实机回归
- 原因：Windows 上启用 Tauri 原生文件拖放处理器时，WebView2 的 HTML5 `draggable` 不可作为可靠的内部排序通道；旧实现同时依赖两者并用全局抑制时间窗隔离，导致内部排序失效后还可能继续压制外部文件事件。外部命中还依赖窄间隔和 `devicePixelRatio`，在系统缩放下不稳定。
- 当前实现：资源管理器路径继续只由 Tauri 原生拖放事件接收，并按窗口真实缩放因子转换坐标；曲目整行按中线计算插入位置。播放列表内部排序使用带移动阈值的整行 Pointer Events 和指针捕获，拖动期间扩展间隔并显示插入线；不再创建 HTML5 可拖对象，也不会触发外部导入路径。拖动框选已删除，批量选择只使用单击、Ctrl 和 Shift，避免与排序争抢手势。产品层独立播放队列已经由 ADR 0018 删除。
- 既定行为：拖到用户播放列表行时追加；拖到曲目间隔时按该位置插入；拖到侧栏播放列表间隔时在对应位置新建列表。内部曲目拖动只能重排，不得触发外部导入。
- 自动验证：浏览器预览已确认默认列表选择、Ctrl 多选、删除选中项状态、播放中侧栏标识和底栏 Hi-Res SVG；59 个普通 Rust 测试覆盖路径分类、默认列表稳定会话 ID、批量删除/清空事务、列表插入/稠密重排、活动列表同步、非活动列表隔离和主窗口几何约束；前端 build 通过且干净会话控制台无 warning/error。
- 默认列表扩展：空列表或曲目滚动区域接收多个文件/文件夹并追加，标题和右侧操作区不命中；文件夹只展开直属音频，重复路径返回拒绝计数。默认列表与用户列表统一使用“添加文件/添加文件夹”菜单；默认列表为当前列表时，同步追加 Rodio 内部序列且不打断当前曲目。
- 剩余验收：Windows 资源管理器向默认列表曲目区、用户列表行、曲目位置和侧栏间隔的真实拖入，以及 100%/125%/150% 缩放下的命中手感由项目所有者确认。

## 主窗口多显示器与 DPI 恢复待实机验收

- 状态：ADR 0020 实现及自动验收完成；窄屏原生切换、多显示器与最大化恢复仍阻塞 0.1.0 实机验收。
- 已解决：Slider 和歌词点击共用递增 seek transaction，命令完成前保持目标值；设置、侧栏、完整播放器歌词/播放信息和窄屏内容已使用 Mantine `ScrollArea`。窄屏使用顶部全局导航与播放列表 Tabs，不再保留重复 Drawer；`120px` 两行底栏使曲目信息/进度与 `44px` Mantine 控件区彼此独立。
- 当前实现：Rust/Tauri 保存显式 `wide`/`compact` 模式及各自正常几何和最大化状态，首次显示前应用最小尺寸与可见工作区约束。React 同步权威模式并完成布局后发送 ready；若前端未 ready，原生 3 秒兜底显示已恢复窗口。
- 自动验证：浏览器覆盖 `1080×700`、`760×520`、`420×720`、`360×600`、中英文和明暗主题；顶部导航、播放列表 Tabs、默认列表内容和两行底栏控制无横向溢出或控制台告警。Windows Release 首次启动生成 `main-window.json`，连续启动与本轮可见性探针均通过且保存的内容区尺寸稳定；约束算法和宽窄独立槽有 Rust 单元测试。
- 剩余验收：在设置中实际切换宽屏/窄屏，分别移动、缩放、最大化并重启；覆盖主屏/副屏、100%/125%/150% DPI 和显示器断开后的可见区域修正。浏览器尺寸测试不能替代该项。

## 桌面歌词原生视觉与多显示器恢复待最终验收

- 状态：核心功能已通过项目所有者 Windows 验收；0.0.15-0.0.17 已实现偏好、位置恢复、滚动语义和首帧优化，原生最终感知仍待发行回归
- 影响：显示、同步、拖动、穿透、原生解锁、退出、运行时入口、文字透明度、hover 交互背景和位置恢复均已接入；多显示器拔插、不同 DPI 和首个透明可见帧无法由浏览器测试完整覆盖。
- 进程判断：桌面歌词不是 sidecar，也没有创建第二份 Rust 播放服务。任务管理器中额外的 renderer/GPU/utility 进程来自 WebView2 多进程架构；Resona 当前仍只有一份 `RodioPlaybackEngine`、队列和歌词服务。
- 剩余验收：跨显示器移动后重启、显示器断开后的可见区域恢复、125%/150% 缩放、透明首帧和原生解锁热点最终手感。
- 处理决定：主窗口关闭即退出、官方单实例、隐藏/退出资源释放、播放区运行时入口、歌词窗口顶部控件、原生 helper hover 显隐和位置持久化均已统一接入。
- 不采用：把当前行为解释为后台播放、临时增加系统托盘、依赖最后一个窗口关闭的隐式推断，或通过移除桌面歌词 WebView 回避生命周期设计。

桌面歌词基本功能已通过验收；两行滚动在 seek/revision/reduced-motion 时直接定位，平台动画不稳定时允许降级为当前行。上述原生场景通过前不把它描述为最终跨显示器形态。

## Windows 原生文件选择窗口偶发阻塞

- 状态：暂缓，不阻塞 0.0.5
- 影响：点击添加或打开文件后，Windows 原生文件选择窗口偶发未正常显示或无响应；主窗口因原生模态关系暂时不可操作。
- 当前实现：Tauri dialog 2.7.1 / rfd 0.16.0，Windows 使用 `IFileOpenDialog`；Tauri 自动设置当前窗口为 parent。前端通过同步 ref 保证同一时间最多发起一次调用，并在等待期间禁用相关按钮。
- 已排除的应用侧问题：快速重复点击造成多个原生对话框叠加；缺少 parent；普通 Promise 异常未恢复 UI 状态。
- 暂缓理由：WebView 不能可靠取消已经进入 Windows COM 模态循环的对话框。JavaScript 超时只能停止等待，不能关闭原生窗口，反而可能错误解锁主界面并叠加下一次调用。

### 重新开启调查的条件

满足任一条件后重新处理：

- 能稳定复现，并能确认触发目录、最近访问位置、网络盘或特定 Shell 扩展。
- Tauri dialog、rfd 或 Windows SDK 发布明确相关修复。
- 阻塞频率达到常用工作流不可接受的程度。
- 开始设计完全内置的文件浏览器，能够减少对原生选择器的依赖。

### 后续诊断路径

1. 用最小 rfd/Tauri 对话框程序与 Resona 对照复现。
2. 分别测试本地目录、断开的网络位置、快速访问、OneDrive 和禁用第三方 Shell 扩展环境。
3. 记录 Windows 版本、Explorer 事件、对话框最后目录和阻塞频率。
4. 只有证明应用线程模型或 parent 绑定存在问题时才修改调用实现。

暂不采用强制超时、后台杀死 Explorer、自动发送窗口消息或无依据地切换到自研文件选择器。
